# Блочный E2E План Проверки Бота

Обновлено: 2026-04-20
Охват: ручная проверка перед заливкой на сервер и перезапуском.

## Блок 0. Старт и здоровье сервисов

1. Перезапусти API и бота.
2. Убедись, что оба сервиса в статусе `active (running)`.
3. Открой чат бота и отправь `/start` от админа.
4. Ожидается:
- бот отвечает без таймаута
- видна кнопка админки

## Блок 1. Вход нового пользователя

1. Новый пользователь (которого нет в БД) отправляет `/start`.
2. Ожидается:
- сообщение о закрытом доступе
3. Новый пользователь отправляет `/start ref_<валидный_user_id>`.
4. Ожидается:
- создается заявка кандидата
- админу приходит карточка с кнопками `approve_/deny_`
- у пользователя статус ожидания

## Блок 2. Одобрение и выдача trial

1. Админ нажимает `approve_<user_id>`.
2. Ожидается:
- пользователь получает текст одобрения
- статус пользователя становится `trial`
- у пользователя появляется `uuid`
- клиент в панели включен

## Блок 3. Отклонение заявки

1. Для другого пользователя админ нажимает `deny_<user_id>`.
2. Ожидается:
- пользователь получает отказ
- статус становится `denied`

## Блок 4. Поддержка (roundtrip)

1. Пользователь отправляет обычный текст боту.
2. Ожидается:
- админу приходит уведомление поддержки + кнопка `reply_<user_id>`
3. Админ нажимает `reply_<user_id>` и отправляет ответ.
4. Ожидается:
- пользователь получает ответ
- запись сохраняется в `support_chat`

## Блок 5. Подтверждение платежа

1. Создай pending-платеж в записи пользователя (`payment_status=pending_*`, сумма, label).
2. Админ нажимает `payok_<user_id>`.
3. Ожидается:
- `payment_status` -> `none`
- `status` -> `active`
- expiry продлен примерно на 30 дней от `max(now, current_expiry)`
- `device_limit` обновлен по target/flex логике
- для `uuid` синхронизирован лимит в панели

## Блок 6. Отклонение платежа

1. Создай pending-платеж тестовому пользователю.
2. Админ нажимает `payno_<user_id>`.
3. Ожидается:
- `payment_status` -> `none`
- `status` -> `denied`
- expiry уходит в прошлое

## Блок 7. Категории админки и базовые действия

1. Открой админку и пройди по категориям `admin_cat_*`.
2. Проверь, что каждая кнопка открывает нужное подменю.
3. Запусти базовые действия:
- `admin_stats`
- `admin_add_slots`
- `admin_backup`
- `admin_restart_xray`
4. Ожидается:
- callbacks отрабатывают без ошибок
- бот отправляет подтверждения

## Блок 8. Безопасность доступа к панели

1. Нажми `admin_panel_unlock` и введи валидный IP.
2. Ожидается:
- подтверждение открытия панели
- запущен таймер автозакрытия
3. Нажми `admin_extend_panel`.
4. Ожидается:
- сессия продлена на TTL
5. Дополнительно проверь предупреждение перед авто-локом и сам авто-лок.

## Блок 9. Текстовые режимы админа

1. Проверь режимы:
- `trial7_user`
- `unlimited_user`
- `extend_user`
- `traffic_limit_user`
- `ban_user` / `unban_user` / `delete_user`
2. Ожидается:
- state machine корректно принимает ввод
- в БД и статусах ожидаемые изменения
- админ получает финальные подтверждения

## Блок 10. VIP-операции

1. Прогони:
- `vip_show`
- `vip_inc`
- `vip_dec`
- `vip_rotate`
2. Ожидается:
- лимиты корректно меняются в БД/панели
- при ротации создается новый `uuid`, старый ключ отключается

## Блок 11. Smoke фоновых задач

1. Проверь, что с ботом стартуют задачи:
- `anti_rkn_task`
- `xray_health_check`
- `expiry_check_task`
- `traffic_limit_task`
- `pending_payment_reminder_task`
- `scheduled_db_backup_task`
2. Ожидается:
- нет crash-loop
- появляются периодические логи

## Блок 12. Финальные критерии приемки

1. После полного прогона нет traceback/ошибок в логах бота.
2. `/start`, поддержка, approve/reject платежей, ядро админки и эффект device-limit работают end-to-end.
3. После рестарта и 10-15 минут простоя сервисы остаются стабильны.
