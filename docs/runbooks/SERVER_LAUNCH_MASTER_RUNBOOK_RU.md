# SERVER_LAUNCH_MASTER_RUNBOOK_RU

Дата: 2026-05-01
Область: backend + bot + api + mini app v2 (после добавления блока от второго чата)

## 0) Цель запуска
Обновить сервер на новый каркас без простоя и с быстрым откатом.

Критерии успеха:
1. Бот отвечает на `/start` по новым сценариям.
2. Оплата -> pending -> approve/deny работают.
3. Лимит устройств корректно меняется по тарифу/доплате.
4. Фоновые задачи запущены (expiry/reminder/reports/backup/reactivation).
5. Karing-файлы и пошаговая инструкция отдаются из бота.

---

## 5) Пошаговый smoke + e2e контроль

### Блок A. Базовая доступность
1. `/api/health` отдает `{"ok": true}`.
2. Бот отвечает на `/start`.
3. Админ-кнопка видна администратору.

Если не ок:
1. проверить env (`GHOST_ADMIN_ID`, токены, пути);
2. проверить ошибки в `journalctl`.

### Блок B. Онбординг
1. Пользователь без инвайта: короткий отказ (закрытый клуб).
2. Пользователь с инвайтом: pending + уведомление админам.
3. `approve_*`: пользователь получает одобрение и инструкцию.

Ожидаемо:
1. старые тексты не всплывают, кроме старых сообщений в истории Telegram.

### Блок C. Оплаты
1. Из mini app отправить `payment/report`.
2. Админ получает карточку pending с реквизитами и кнопками `payok/payno`.
3. `payok`: пользователь получает “взнос принят...”, админу приходит итог с деталями.
4. `payno`: пользователь получает отказ, админу приходит итог отказа.

Проверка инвариантов:
1. `device_limit` меняется по целевому тарифу.
2. `expiry` продлевается корректно.
3. двойное нажатие не ломает состояние (`already processed`).

### Блок D. Устройства
1. На Solo/Flex проверить добавление/удаление/ротацию устройства.
2. Проверить, что лимит в UI = лимиту в БД.

### Блок E. Karing
1. Кнопка `Настройка Karing` запускает шаги.
2. Шаг 6 показывает `6.jpg` (карандаш на главном экране).
3. Кнопки скачивания отдают 2 нужных файла.

### Блок F. Коммуникация
1. Пользователь пишет в поддержку.
2. Админ отвечает через `reply_*`.
3. `close_*` закрывает тему; новое сообщение пользователя снова открывает тему.

### Блок G. Админка
Проверить только 3 раздела:
1. `Коммуникации`
2. `Безопасность`
3. `Система`

### Блок H. Фоновые задачи
Проверить, что запущены без падения:
1. `expiry_check_task`
2. `pending_payment_reminder_task`
3. `monthly_admin_report_task`
4. `dead_souls_prompt_task`
5. `reactivation_nudge_task`
6. `scheduled_db_backup_task`
7. `db_maintenance_task`

## 7) Что делать при ЧС (rollback)

### 7.1 Быстрый rollback кода
```bash
cd /opt/ghostlink
# пример: выбираешь нужный pre_* каталог
cp -a backups/release/pre_YYYY-MM-DD_HH-MM-SS/* /opt/ghostlink/
sudo systemctl restart ghost-api
sudo systemctl restart ghost-bot
```

### 7.2 Rollback БД
```bash
cd /opt/ghostlink
cp -a backups/db/ghost_users_YYYY-MM-DD_HH-MM-SS.db ghost_users.db
sudo systemctl restart ghost-api
sudo systemctl restart ghost-bot
```

### 7.3 Критерий аварийного отката
Откатываться сразу, если:
1. бот не стартует;
2. массово ломается `/start`;
3. оплата/approve перестают работать;
4. неверно продлеваются сроки у пользователей.

## 8) Ответы на важные вопросы

### 8.1 Есть ли лимит мест по людям
Нет. Лимиты по количеству пользователей отключены (`unlimited_users=true`), новых пользователей можно добавлять без потолка.

### 8.2 Можно ли сделать "команду в боте, которая откатит все на старый каркас"
Технически можно, но в проде это рискованно и небезопасно:
1. команда должна иметь root/systemctl и доступ к файловой системе;
2. высокий риск случайного/вредоносного отката;
3. сложнее контролировать целостность.

Рекомендованный вариант:
1. оставить rollback через серверные команды (раздел 7);
2. в боте сделать только “подготовить rollback-план / показать последний backup tag”, но не выполнять системный откат автоматически.

### 8.3 Как добавить новых админов/модераторов
Роли:
1. `owner` — главный админ (из `GHOST_ADMIN_ID`, задается env).
2. `admin` — полный административный доступ.
3. `moderator` — ограниченный админ-доступ по ролевым правилам.

Порядок:
1. Открыть админский mini app (под owner/admin).
2. Вызвать роль API:
   - список ролей: `GET /api/admin/access/roles`
   - назначить роль: `POST /api/admin/access/roles/set` с `{"tg_id":"<ID>","role":"admin|moderator"}`
   - удалить роль: `POST /api/admin/access/roles/remove` с `{"tg_id":"<ID>"}`
3. Проверить, что пользователь появился в списке ролей с нужной ролью.

Ограничения:
1. Назначить `owner` через API нельзя (owner = только `GHOST_ADMIN_ID`).
2. Все изменения ролей логируются в admin audit.

## 9) Блок Mini App v2 (GitHub + Server + Telegram switch)

Цель блока: безопасно выкатить `webapp-mini-v2`, проверить в реальной работе, и только потом переключить всех пользователей.

Важно:
1. `mini app v2` (frontend) живет в GitHub/статике.
2. backend/bot живут на сервере.
3. Они не "сцепляются сами": нужно отдельно выкатить frontend URL и отдельно обновить backend.

---

### 9.1 Preflight перед выкладкой (локально, до сервера)

Что проверить:
1. В `webapp-mini-v2/src/main.js` отключен preview:
   - `ADMIN_PREVIEW_MODE = false`
2. Нет кракозябр в UI-текстах:
   - все файлы UTF-8, `<meta charset="UTF-8">` в `index.html`.
3. Критичные экраны открываются:
   - `Главная`
   - `Поддержать проект`
   - `Мои ключи`
   - `Пригласить в клуб`
   - `Админка` (только для админа)
4. TODO синхронизирован с фактом, нет "висячих" задач перед релизом.

Если ошибка:
1. JS ошибка в консоли -> исправить в коде до пуша.
2. Кракозябры -> пересохранить файл в UTF-8 (без BOM), проверить API-ответы с `charset=utf-8`.
3. Экран не открывается -> проверить `router.push/show`, id кнопки и id экрана.

Критерий "идем дальше":
1. UI без runtime-ошибок.
2. Все кнопки переходов работают.

---

### 9.2 Выкладка Mini App v2 на GitHub

Рекомендуемый способ:
1. Коммитить изменения в отдельную ветку (`release/mini-v2` или текущий release branch).
2. После ревью/проверки слить в целевую ветку деплоя.

Что именно выкладываем (frontend):
1. папка `webapp-mini-v2/` целиком;
2. если используется отдельный Pages-repo/branch - синхронизировать туда содержимое `webapp-mini-v2`.

Проверка после пуша:
1. открывается публичный URL (например, GitHub Pages или ваш static URL);
2. в `Network` все ресурсы 200 (`index.html`, `src/main.js`, `src/styles.css`, модули);
3. нет 404 на пути ассетов.

Если ошибка:
1. `404` на ресурс -> проверить относительные пути `./src/...` и структуру публикации.
2. белый экран -> открыть DevTools, исправить первый JS exception.
3. старая версия страницы -> hard reload + cache clear + проверить, что открылся новый commit.

Критерий "идем дальше":
1. mini app v2 URL сам по себе стабильно открывается.

---

### 9.3 Подготовка сервера под v2 (backend)

Перед переключением Telegram URL сервер должен уже уметь обслуживать v2.

Обязательные backend endpoint'ы:
1. `/api/user`
2. `/api/payment/settings`, `/api/payment/report`
3. `/api/device/list`, `/api/device/add`, `/api/device/remove`, `/api/device/refresh`, `/api/device/reset`
4. `/api/referrals`
5. `/api/invite/create`, `/api/invite/list`, `/api/invite/revoke`
6. `/api/admin/*` (по ролям)
7. `/api/app-version`

Дополнительно:
1. CORS разрешает origin frontend URL v2.
2. Секреты только в `.env` (не в Git).
3. Панель VPN не доступна публично, только по allowlist/firewall.

Если ошибка:
1. `blocked by CORS policy` -> добавить frontend origin v2 в allowlist CORS на backend и перезапустить API.
2. `401/403` у валидного админа -> проверить Telegram auth и `GHOST_ADMIN_ID`.
3. `404` на `/api/...` -> сервер не обновлен нужной версией, проверить заливку файлов и роуты.

Критерий "идем дальше":
1. backend отвечает на все endpoint'ы, нужные mini app v2.

---

### 9.4 Канареечный запуск (только админ-аккаунт)

Зачем:
1. проверить боевой контур без влияния на всех пользователей.

Как:
1. Временно дать новый URL mini app v2 только в админском тестовом сценарии (через отдельную кнопку/временную команду/тест-бота).
2. Пройти e2e вручную админом.

Минимальный e2e канарейки:
1. Главная: статус подписки, переходы.
2. Поддержать проект: выбор периода/тарифа, открытие окна оплаты, отправка report.
3. Мои ключи: add/refresh/remove/reset + копирование.
4. Пригласить в клуб:
   - прямой invite
   - bridge create/revoke
   - реферальный отчет
5. Админка:
   - dashboard/users/devices/payment/panel/system
   - роли и история реквизитов.

Если ошибка:
1. критичная (невозможно платить/выдавать ключи) -> не переключать массово, исправлять и повторять канарейку.
2. некритичная UI-ошибка -> фикс, повторный проход только затронутых сценариев + smoke всего контура.

Критерий "идем дальше":
1. Канарейка без критичных багов.

### 9.5 Массовое переключение Telegram WebApp URL на v2

Делать только после канарейки.

Шаги:
1. Обновить URL mini app в настройках бота на frontend v2.
2. Зафиксировать время переключения (для мониторинга).
3. Первые 15-30 минут активно смотреть логи API/bot и ошибки клиентов.

Что мониторить:
1. рост 4xx/5xx;
2. CORS ошибки;
3. падения `/api/payment/report`, `/api/device/*`, `/api/invite/*`.

Если ошибка после массового переключения:
1. быстрый откат URL mini app обратно на v1;
2. продолжить разбор уже без влияния на всех пользователей;
3. после фикса повторить канарейку и только потом повторное переключение.

### 9.6 Детальный чек ошибок и быстрые фиксы

#### A) Mini app открывается, но "Ошибка сети. Попробуй еще раз."
Причина:
1. backend недоступен;
2. CORS;
3. неверный API base URL.
Действия:
1. проверить `/api/health`;
2. проверить CORS headers (`Access-Control-Allow-Origin`);
3. проверить конфиг API base в frontend.

#### B) Вкладка "Пригласить в клуб" не создает мост
Причина:
1. не готов `/api/invite/*`;
2. bridge endpoint не развернут.
Действия:
1. проверить `/api/invite/create`;
2. проверить логи backend на invite/bridge route;
3. проверить TTL/rate-limit/revoke конфиг.

#### C) QR/link отображается, но гость не проходит цепочку
Причина:
1. токен истек;
2. bridge session не закрывается корректно;
3. временный ключ не создается/не удаляется.
Действия:
1. проверить записи invites/bridge_session;
2. проверить integration с 3x-ui/panel API;
3. проверить cron cleanup.

#### D) Админка недоступна у owner
Причина:
1. неверный `GHOST_ADMIN_ID`;
2. auth telegram headers не приходят;
3. role map поврежден.
Действия:
1. сверить `GHOST_ADMIN_ID` в env;
2. проверить backend auth middleware;
3. проверить `_meta.admin_roles` и `_meta.admins`.

---

### 9.7 Финальная приемка "готово к бою"

Ставим "готово", если выполнено все:
1. frontend v2 доступен по боевому URL.
2. backend обновлен и совместим с v2 API.
3. CORS настроен для v2 origin.
4. канареечный e2e пройден.
5. массовое переключение выполнено без критичных регрессий.
6. rollback-путь проверен и занимает минуты, а не часы.

---

### 9.8 Короткий fallback-план (если стало плохо сразу после релиза)

1. Немедленно вернуть WebApp URL на v1.
2. Проверить здоровье API/bot (`/api/health`, `journalctl`).
3. Зафиксировать инцидент: время, симптом, последний деплой/коммит.
4. Исправить проблему в v2, повторить 9.1 -> 9.4.
5. Повторно переключить пользователей только после успешной канарейки.
