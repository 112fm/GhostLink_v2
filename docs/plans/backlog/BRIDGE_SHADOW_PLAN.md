# BRIDGE SHADOW PLAN

## Статус

Backlog (проектирование завершено, реализация не начата).
Обновлено: 18.04.2026.

## Цель

Дать приглашенному пользователю доступ в клуб даже при проблемном Telegram:
1. через обычный инвайт (Standard),
2. через веб-мост (Bridge) с временным ключом и последующим рукопожатием в боте.

## Бизнес-режимы

1. Standard Invite:
- ссылка `t.me/...start=<token>`;
- валидация токена в боте;
- при валидном токене автоматический допуск в базовый flow.

2. Bridge Invite:
- ссылка/QR на веб-страницу моста;
- выдача временного ключа с TTL и лимитом трафика;
- переход в бот;
- автоматическая миграция на постоянный профиль и удаление временного.

## Принятые технические принципы

1. База данных:
- таблица `invites`;
- таблица `bridge_sessions`;
- все поля и индексы должны создаваться безопасно (`CREATE TABLE/INDEX IF NOT EXISTS`).

2. Безопасность:
- короткий TTL инвайтов;
- rate limiting на bridge-endpoint;
- одноразовое/ограниченное использование токена;
- журналирование ключевых событий (`invite_created`, `bridge_issued`, `bridge_handshake_done`).

3. Рефералка:
- связь `inviter -> invited` фиксируется при активации токена;
- начисление бонуса только после первой успешной оплаты приглашенного.

4. Маскировка/стелс:
- обсуждение и внедрение только отдельным этапом после базовой рабочей версии;
- без преждевременного усложнения текущего прода.

## Этапы реализации

1. Этап A (storage + contracts):
- подтвердить финальные поля `invites/bridge_sessions`;
- описать API-контракты (`/api/invite/create`, `/api/invite/list`, `/api/invite/revoke`, `/bridge/i/<token>`).

2. Этап B (standard invite hardening):
- стабильная проверка токена в боте;
- корректная блокировка неинвайтных входов.

3. Этап C (bridge issue flow):
- endpoint выдачи временного ключа;
- TTL/лимит и запись в `bridge_sessions`.

4. Этап D (handshake):
- при `/start` в боте найти bridge-сессию;
- удалить временный ключ в панели;
- создать/активировать постоянный профиль;
- закрыть bridge-сессию.

5. Этап E (операционка):
- cron-очистка просроченных токенов/временных профилей;
- runbook для инцидентов bridge.

## Ограничения на старт

Реализацию Bridge не начинать, пока:
1. не закрыты критичные P0 в активном плане (оплаты/лимиты/ключи),
2. не проведена отдельная сессия согласования API + UX + security с владельцем.
